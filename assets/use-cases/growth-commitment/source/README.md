# Growth commitments through the CLI

This example compares complete growth arrangements for a business selling one
standardized service package. It starts with $12,000 of available growth cash,
140 delivery hours, a $1,500 collected price and $500 of delivery expense per
customer. Each customer requires five delivery hours.

The campaign quote is a committed expense. Fewer customers reduce delivery work
and receipts; they do not refund the campaign. Customer counts and collection
dates are supplied assumptions rather than forecasts generated by Decision Lab.

| Arrangement | Committed campaign | Assumed customers | Peak funding needed | Delivery hours | Operating finding |
| --- | ---: | ---: | ---: | ---: | --- |
| Keep the current approach | $0 | 0 | $0 | 0 | Fits |
| Large campaign, invoice after delivery | $8,000 | 40 | $28,000 | 200 | Cash and capacity blocked |
| Small campaign, invoice after delivery | $2,000 | 10 | $7,000 | 50 | Fits |
| Medium campaign, payment before delivery | $4,000 | 20 | $4,000 | 100 | Fits |

The prepaid arrangement still costs $14,000 for campaign and delivery. Its
$4,000 funding requirement is lower because customer cash arrives before the
delivery payment. The large arrangement ends with more cash than it started
with, but its earlier deficit still prevents execution. The operating model
compares feasibility and deliberately selects no preferred arrangement.

Dates on zero-value cash placeholders create no future obligation. A positive
committed campaign payment still has to fit the horizon when sales are zero.

## Run the complete example

Use Node.js 22.19 or later and the `@decision-lab/sdk` and `@decision-lab/cli`
packages containing the ordered cash-flow contract. This example records their
exact versions and package hashes in its output. In the Decision Lab source
workspace, first run `npm run build:packages`. A standalone copy can install its
listed npm dependencies once those package builds are available.

Read [the fictional authoring judgments](source/authoring-reviews.json), then:

```sh
node walkthrough.mjs all --accept-fictional-demo --output-root /tmp/growth-example-1
```

The output directory must be new or empty. A stage refuses to overwrite retained
work. The consent flag only replays the supplied authoring judgments; it does
not approve a business commitment or require case workers to review answers.

The same sequence can be run separately:

```sh
node walkthrough.mjs author --accept-fictional-demo --output-root /tmp/growth-example-2
node walkthrough.mjs cases --output-root /tmp/growth-example-2
node walkthrough.mjs changes --output-root /tmp/growth-example-2
node walkthrough.mjs learning --output-root /tmp/growth-example-2
```

Every stage writes `commands.json`, a readable `commands.sh` transcript and
`verification.json`. The script calls the public CLI command runner. It does not
call an internal evaluator, browser storage or repository-only publishing code.

## What the files mean

| File | Responsibility |
| --- | --- |
| [profile.json](profile.json) | Author-owned arrangement identities, payment meanings and starting values |
| [model.mjs](model.mjs) | Compiles that bounded profile into the canonical commitment model; performs no evaluation |
| [workflow.mjs](workflow.mjs) | Declares questions, mappings, next actions and shared report views |
| [learning.mjs](learning.mjs) | Authors the optional nonbinding preference-test model and prepares source-backed operating eligibility |
| [fixtures/cases.mjs](fixtures/cases.mjs) | Complete fictional native cases and deliberate missing-input examples |
| [source/growth.model.json](source/growth.model.json) | Complete canonical operating rules and initial inputs consumed by `app init` |
| [source/learning.model.json](source/learning.model.json) | Complete learning model, explicit probabilities and hashed before/after operating findings |
| [source/workflow.source.json](source/workflow.source.json) | Portable workflow source with exact supporting app pins |
| [cases/baseline.json](cases/baseline.json) | Shared inputs for one workflow calculation |

JSON files are also valid YAML. The CLI accepts either representation. App
definitions and cases are separate: changing an admitted quote, count, date,
reserve or capacity does not require republishing the rules.

## Author the apps and their workflow

The `author` stage recreates both templates and both app packages. For example:

```sh
decision-lab app init --template source/commitment.template.json \
  --model source/growth.model.json --app-id compare-growth-arrangements \
  --release 1 --format json --output growth.app-definition.json
decision-lab app validate growth.app-definition.json
decision-lab app pack growth.app-definition.json \
  --created-at 2026-11-22T18:00:00.000Z --output growth.app.json
decision-lab workflow create --source source/workflow.source.json \
  --output growth.workflow-definition.json
```

The walkthrough checks that the recreated packages equal the supplied packages,
including their content hashes. The workflow source pins those exact apps.
Changing an app requires deliberately updating its workflow dependency.

An installable workflow additionally goes through `workflow draft`,
`workflow inspect-draft`, an explicit `workflow review-binding` for each exact
binding, and `workflow pack`. The frozen review journal explains meaning, scope
and units separately for each binding. A changed binding hash stops the replay.
The final Excel input package is recreated with `workbook pack` against that
workflow package.

The commitment template is authoring version 1.1.0. It retains the installed
Complete a Commitment pattern while allowing this bounded aggregate workload
model to declare period-capacity predicates without inventing detailed tasks.

## Calculate a case and keep the complete output

```sh
decision-lab workflow start --definition growth.workflow-definition.json \
  --case cases/baseline.json --run-id growth-example \
  --created-at 2026-11-22T18:00:00.000Z --output started.run.json
decision-lab workflow solve --run started.run.json \
  --created-at 2026-11-22T18:00:00.000Z --output calculated.run.json
decision-lab workflow inspect --run calculated.run.json --output output.json
decision-lab workflow brief --run calculated.run.json --format markdown \
  --output decision-brief.md
```

`output.json` contains the current planning assessment, ordered cash ledgers,
scenario-specific operating findings, report projections, decision process and
next actions. The Markdown brief is a readable projection of that same run.
Shared UI components render these contracts; the example adds no custom React
report or domain-specific solver.

The `cases` stage checks weak demand, zero sales, low cash, reserve protection,
capacity shortages, late payment, missed cutoffs and nonpositive contribution.
A completed blocked business outcome is a successful calculation. A missing
required cash value remains unavailable and returns CLI exit 3.

The campaign hurdle is a separate conditional result: the $4,000 campaign needs
four genuinely additional customers at $1,000 contribution each to cover its
expense; five is the first whole count exceeding expense. This arithmetic does
not establish customer response or a causal marketing effect.

## Change an input and reassess

The `changes` stage branches the saved baseline. Lower opening cash to $1,000
and only the no-expansion alternative remains usable. Lower delivery capacity
to 80 hours and the smaller invoiced campaign remains usable while the medium
prepayment arrangement fails capacity.

`workflow answer` marks the affected findings stale. `workflow solve` calculates
again and retains earlier evaluations. Marking opening cash `unknown` removes
the value rather than substituting zero. The original saved run is unchanged.

## Test a payment assumption before committing

The optional learning case compares two explicit customer-response situations.
The prepayment offer has 20 customers in one situation and two in the other.
The invoice alternatives retain their supplied counts. Fictional 50/50 priors,
an imperfect favorable/unfavorable/inconclusive signal matrix, a $500 fee and a
one-day delay are all recorded inputs.

Under those assumptions, choosing now has $8,000 expected contribution. A timely
test followed by a complete response has $9,800 after its fee, an improvement of
$1,800. A favorable signal leads to the medium prepayment arrangement; an
unfavorable or inconclusive signal retains the small invoiced arrangement.

The `learning` stage verifies these calculations through the workflow and the
standalone learning app. It then delays the test beyond the commitment cutoff:
new growth responses become unavailable and choosing now is preferred. Missing
optional probability assumptions leave learning unavailable while preserving
the complete operating comparison.

The test collects no orders or money. A paid pilot would create cash and
delivery obligations and needs a complete authored operating model. None of
these fictional probabilities establish real customer behavior.

## Continue in Decision Lab

The `author/growth.workflow.json` and `author/growth.workbook.json` outputs are
portable packages. In **Collections → Import app, workflow or case**, import the
Excel input package to install its embedded workflow together with the Excel
interface, or import the workflow package alone. The retained
`*.solved.run.json` files are workflow runs for the exact definition; use
**My cases → Import workflow run** to continue one of those calculations.
Packaging does not publish, install, collect payment or commit campaign spending.

For another service package, change only the worker values admitted by the
published input schema. Different installment terms, refund obligations,
multi-period customer delivery or an additional arrangement require an authored
model and dependency revision. Review the changed mappings before publication.
