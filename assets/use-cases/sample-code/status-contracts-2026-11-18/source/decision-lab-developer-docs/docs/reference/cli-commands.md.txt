# CLI command reference

Applies to `@decision-lab/cli` **0.1.0**, using `@decision-lab/sdk` **0.1.0**. Requires Node **22.12.0 or later**. See [CLI usage](../../CLI.md) for the complete first-run example.

The registered executable is `decision-lab`. In an npm project with a local installation, invoke it as `npm exec --offline -- decision-lab ...`.

```sh
decision-lab --help
decision-lab --version
decision-lab run --help
```

`--version` prints both CLI and resolved SDK versions. Each command supports `--help` or `-h`; `template`, `composition`, `collection`, `comparison`, `app`, `case`, `workbook`, and `workflow` also provide grouped help.

## Common output behavior

- `--output FILE` writes an artifact to a file. Omit it, or use `--output -`, for stdout.
- Definitions and initialized case inputs are YAML. Packages, receipts, assessments, and complete runs are JSON.
- Errors are JSON diagnostics on stderr. Do not infer a successful business result from an empty stderr stream.
- Output files are written atomically. Parent directories must already exist.
- Existing files are refused unless a replaceable output is given `--force`. Template/app/workflow/collection packages, sealed composed templates, generated compositions, and `app open`/`workflow package-open` output remain immutable even with `--force`; choose a new output path.
- `--created-at` requires an ISO timestamp with seconds and a timezone. `--run-id` supplies a stable ordinary identifier. These control provenance, not the underlying decision inputs.

Options accept `--name VALUE` or `--name=VALUE`. Most options cannot be repeated. `--require-module-field` and workflow authoring `--published` are repeatable. Boolean flags `--force` and `--recompute-prior` do not take values.

## Edit commitment requirements

```text
decision-lab app rules --model MODEL.yaml [--output FILE] [--force]
decision-lab app rules-preview --model MODEL.yaml --edits EDITS.yaml
  [--output FILE] [--force]
decision-lab app rules-apply --model MODEL.yaml --edits EDITS.yaml
  --output NEW.model.yaml [--force]
```

These authoring commands use the public SDK's `appRules` service. Inspection
returns the supported requirements, conditions and declared input vocabulary.
Preview returns validated candidate `model`, canonical YAML `source`, hashes,
changed declarations and `caseValidation`. Apply writes that exact `source` to
a separate native model file. Neither command evaluates a case, publishes an
app, increments a module version or updates installed apps/workflow pins.

Edits use `decision-lab-app-rule-edits/1`, exact `baseModelHash`, and 1–32
explicit `changes`. Supported changes set a mandatory requirement, set a scalar
comparison or matching-record condition, or add a typed parameter/table with
explicit starter data. Conditions may apply only to selected declared choices.
Other expression trees remain intact; guided edits cannot replace advanced
conditions they do not understand. See the runnable
[requirements walkthrough](../guides/edit-app-requirements.md).

Invalid edits or module declarations fail with exit `2` and no candidate file.
An otherwise valid candidate with invalid starter case data returns exit `2`:
preview exposes its validation receipt; apply can retain the separate repairable
YAML draft with an `APP_RULE_CASE_INVALID` stderr diagnostic naming that file
and listing its case issues. Inspect preview and correct those inputs before publication. Apply
requires a file output; inspection and preview permit JSON stdout. No output can
replace the model or edits file, including linked aliases and with `--force`.
Only supported complete-commitment models can be edited. Inspection of another
pattern reports `supported: false` and its reason.

## Check an app's business scenarios

```text
decision-lab app check --app APP.json --suite SUITE.yaml
  [--timeout-ms INTEGER] [--run-id ID] [--created-at ISO_TIMESTAMP]
  [--output FILE] [--force]
```

The separate `decision-lab-app-check-suite/1` file identifies its `id`, `title`
and installed `pattern`. Each entry in `scenarios` supplies `id`, `title`,
complete case `inputs`, and a nonempty `expect` list. Optional scenario
`description` and expectation `id`/`title` explain the business purpose.
Expectations address evidence questions, learning recommendations/study
feasibility, or complete commitment plans/constraints. See the runnable
[author scenario walkthrough](../guides/check-an-adapted-app.md).

The SDK validates all scenarios against the selected app before execution.
Invalid suites or case inputs return a validation receipt and exit `2`.
Otherwise the command produces `decision-lab-app-check-result/1`, with expected
and actual findings, each scenario's execution status, and exact app/model,
suite and SDK bindings. It does not duplicate full report bundles, publish an
app or record approval. `--timeout-ms` applies to each scenario. This command
does not expose pattern-specific search-limit flags.

Exit `0` means every expectation passed; `1` means a completed expectation
mismatch; `3` means a required result is unavailable or execution stopped;
`4` means an operational or delivery failure. Result files are replaceable
with `--force`, but can never replace an app or suite input, including linked
aliases. Omit `--output` for JSON stdout. An ordinary completed `run` keeps its
existing exit behavior even when the business finding is blocked or unresolved.

## Excel workbooks

See the [Excel guide](../guides/work-with-case-workbooks.md) and
[mapping contract](case-workbook-mapping.md). Use `decision-lab workbook --help`
for complete command signatures.

Authors package the interface once; workers use the installed release without
mapping configuration:

```text
decision-lab workbook pack --target TARGET.json [--mapping MAP.json]
  [--starter CASE.yaml] [--starter-meaning example|defaults] --output RELEASE.json
decision-lab workbook start --release RELEASE.json (--case-id ID|--run-id ID)
  [--created-at ISO] --output CASE_OR_RUN.json
```

Packing proves an unchanged starter round trip. Starting creates an independent
app case or unreviewed workflow run; it does not reuse another case's identity.

| Target | Commands | Required installed-release context | Import output |
| --- | --- | --- | --- |
| Standalone app | `workbook export`, `preview`, `validate`, `import` | `--release --case --revision` | Separate canonical case YAML. |
| Guided workflow | `workbook workflow-export`, `workflow-preview`, `workflow-validate`, `workflow-import` | `--release --run` | Separate native run JSON; changed typed answers await review. |
| Shared comparison | `workbook comparison-export`, `comparison-preview`, `comparison-validate`, `comparison-import` | `--release --case --case-id --revision` | Separate shared-case JSON; preparation remains explicit. |

Authors/integrators may instead supply `--app --mapping`, `--workflow --mapping`
or `--comparison --mapping` in place of `--release`. Mixing those configuration
modes is rejected. Omitting `--mapping` during `pack` generates a draft from
supported declared input structures; authors review its editable coverage.

Export requires file `--output`, with optional `--exported-at`. Preview,
validation and import require `--workbook` and accept optional `--manifest`.
Preview returns `{receipt,candidate?}`; validation returns only the receipt.
Rejected values exit 2. Import also requires file `--output`; workflow import
accepts `--at` for its answer transitions. No workbook command can overwrite
any input path or link alias, even with `--force`. No command accepts an answer,
reviews findings, evaluates an app or mutates stored UI data. Workflow conflicts
use the exact sealed run and its native revision; there is no workflow
`--revision` flag. Other targets use explicit case identity/hash and revision.

## Collections

Collections are organization metadata, with exact typed app/workflow references.
They do not replace product packages, authoring reviews or reasoning contracts.
All collection artifacts and outputs are JSON. See the
[collection guide](../guides/manage-a-collection.md).

```text
decision-lab collection create --source SOURCE.json --output FILE [--force]
decision-lab collection validate --source DEFINITION_OR_PACKAGE_OR_INSTALLATION.json
  [--output FILE] [--force]
decision-lab collection pack --source DEFINITION.json [--created-at ISO]
  --output FILE
decision-lab collection open --package COLLECTION.json [--output FILE]
decision-lab collection add-use-case --collection DEFINITION_OR_INSTALLATION.json
  --source USE_CASE.json --output FILE [--expected-revision INTEGER] [--force]
decision-lab collection add --collection DEFINITION_OR_INSTALLATION.json
  --package APP_OR_WORKFLOW.json --use-case ID [--artifact DESCRIPTOR.json]
  --output FILE [--expected-revision INTEGER] [--force]
decision-lab collection remove --collection DEFINITION_OR_INSTALLATION.json
  --type app|workflow --id ID --output FILE [--expected-revision INTEGER] [--force]
decision-lab collection install --package COLLECTION.json --output FILE [--force]
decision-lab collection inspect --collection DEFINITION_OR_PACKAGE_OR_INSTALLATION.json
  [--output FILE] [--force]
decision-lab collection plan-update --collection INSTALLATION.json
  --package COLLECTION.json [--output FILE] [--force]
decision-lab collection update --collection INSTALLATION.json --package COLLECTION.json
  --output FILE [--expected-revision INTEGER] [--force]
```

`create` accepts publisher/collection identity, version, title/description, use
cases and optional initial members/metadata. `add` derives exact pins by opening
the supplied app/workflow package. An optional descriptor contains relative
`path`, file `bytes` and wire-file `sha256`; it does not fetch or verify a file at
that path. `pack` seals a collection, with a reproducible explicit timestamp.
`validate` checks any of the three forms; `open` verifies a sealed package.

`install` writes a **portable membership state only**. It downloads no products,
starts no evaluator and changes no UI store. Local use cases/members/exclusions
live separately from the exact upstream base. `add-use-case`, `add` and `remove`
operate on the local overlay when supplied installed state. `remove` remembers
an upstream exclusion; it deletes no independent product or case.

`plan-update` returns an inspectable plan with `canApply` and conflicts, exiting
0 even when explicit resolution is needed. Applying a conflicting update exits
2 and delivers no new state. Updates preserve local members/use cases/exclusions
and require the same scoped collection identity plus a newer stable version.

`--expected-revision` accepts a nonnegative integer for installed-state edits
and updates. It checks the input artifact, not a shared filesystem or store.
The caller owns concurrency. Prefer fresh outputs; deliberate `--force` can
replace editable definitions/states, while `pack` and `open` outputs remain
immutable. An invalid validation receipt exits 2; operational/delivery failures
retain the normal CLI exit 4 behavior.

## Compare authored rules

These commands delegate to the pure SDK comparison service. They prepare
inputs or compare retained results; they perform no native evaluation or
workflow review. See the [worked guide](../guides/compare-authored-rules.md).

```text
decision-lab comparison create --source SOURCE.json --output FILE
decision-lab comparison validate --source ARTIFACT.json [--output FILE] [--force]
decision-lab comparison open --source ARTIFACT.json [--output FILE]
decision-lab comparison inspect --source ARTIFACT.json [--output FILE]
decision-lab comparison prepare --comparison DEFINITION.json --case CASE.json
  [--preparation-id ID] [--created-at ISO] --output FILE
decision-lab comparison inputs --preparation PREPARATION.json --variant ID
  [--output FILE] [--force]
decision-lab comparison compare --preparation PREPARATION.json --results RESULTS.json
  [--max-output-bytes INTEGER] [--output FILE] [--force]
```

`create` seals author-declared meanings, schema, shared fields, exact-pinned
variants, complete input mappings and output measures. `prepare` retains one
shared case, maps/validates it for each product and emits bound app snapshots
or seeded workflow runs. `inputs` extracts the selected ready seed. Continue
through the ordinary `run` or `workflow` commands to obtain native results.

`RESULTS.json` is an array of `{variantId, run}` containing full native JSON
objects, not paths. `compare` verifies those runs against the exact preparation
and retains their complete reports alongside declared comparable findings.
Missing results stay pending. It cannot mark workflow results reviewed, treat
unfinished work as available, or infer a universal score or winner.

`open`, `inspect` and `validate` accept all three artifact forms through
`--source`. `open`/`inspect` return the verified normalized artifact, not a
lossy summary. `validate` returns `{valid, issues}` and exits `2` when invalid.
An unready preparation or incomplete native comparison delivers its complete
qualified artifact with exit `3`. Intentional measure unavailability does not
prevent completion when all native variants are available. Integrity, product
or input substitutions exit `2` without publishing a partial artifact.

`create`/`prepare` require `--output`; `-` selects stdout. These operations and
`open`/`inspect` cannot overwrite a file, even with `--force`. Compare outputs,
validation receipts and extracted input snapshots permit deliberate replacement.
The 50 MB artifact ceiling includes embedded native reports. `compare` can
lower final delivery size with `--max-output-bytes` in `1..50000000`; delivery
failure exits `4` atomically. Existing same-release historical comparisons and
collection organization remain separate contracts.

## Templates

```text
decision-lab template init --pattern PATTERN --id ID --version VERSION --title TITLE
  [--description TEXT] [--guidance TEXT] [--require-module-field PATH ...]
  [--output FILE] [--force]

decision-lab template validate DEFINITION.yaml [--output FILE] [--force]

decision-lab template pack DEFINITION.yaml [--created-at ISO_TIMESTAMP] [--output FILE]
```

`PATTERN` is `evidence-review/1`, `assess-value-of-learning/1` or `complete-a-commitment/1`. `VERSION` is a semantic version such as `1.0.0`. `init` emits an editable definition with the installed contract. Required module paths add presence restrictions for known fields; they cannot replace the evaluator or supply arbitrary code.

`validate` emits `{ valid, issues }` and returns exit `2` for an invalid definition. `pack` verifies the definition and emits a content-hashed immutable template package.

## Composed templates

A composed template declares how author choices produce several pinned apps and
their workflow. It is a separate artifact from a single-pattern template. Its
JSON declarations contain schemas, pinned single-pattern templates, model
recipes, workflow mappings, and catalog placement. They supply business meaning;
the CLI adds no behavior based on an app's name.

```text
decision-lab composition create --source SOURCE.json --output TEMPLATE.json
decision-lab composition open TEMPLATE.json [--output FILE]
decision-lab composition validate --template TEMPLATE.json
  [--config CONFIG.json] [--case CASE.json] [--output FILE] [--force]
decision-lab composition generate --template TEMPLATE.json --config CONFIG.json
  --created-at ISO_TIMESTAMP --output BUNDLE.json
```

`create` seals an authored `decision-lab-composed-template/1` declaration.
`open` verifies its integrity. `validate` checks the sealed template and any
supplied author configuration or case against its declared schemas; it emits
`{ valid, issues }` and exits `2` when validation fails. This does not certify
the business meaning of a rule or binding.

`generate` uses the author configuration to produce a portable
`decision-lab-composition/1` JSON bundle. It includes the generated `apps`,
component models, manifest, and an **unreviewed** `workflowDraft`. The required
`--created-at` fixes generation metadata; the same template, configuration, and
timestamp produce the same bundle. Generation uses the public SDK, requires no
executor, and evaluates no business case.

The generated draft enters the normal authoring review sequence:

```sh
node --input-type=module -e 'import fs from "node:fs"; const bundle = JSON.parse(fs.readFileSync("generated.json", "utf8")); fs.writeFileSync("generated.draft.json", JSON.stringify(bundle.workflowDraft));'
decision-lab workflow inspect-draft --draft generated.draft.json
# Review each reported binding using workflow review-binding.
decision-lab workflow pack --draft generated.draft.json --output reviewed.workflow.json
```

Generation does not create review receipts. An unreviewed generated draft cannot
be packed through the authoring publication gate. After deliberate review,
the existing workflow commands run the pinned definition with different case
inputs. Changing a record, quote, owner, availability, or deadline does not
require regenerating an app when the published schema already admits that
input. Changing task structure, policy, or mappings requires a new authored
configuration and reviewed release.

`create`, `open`, and `generate` produce immutable artifacts; `--force` cannot
replace an existing file. Generation and composition delivery use the same
50,000,000-byte artifact ceiling as workflows. Invalid declarations or arguments
exit `2`; operational or output-delivery failures exit `4`, with no partial
output file.

## Apps

```text
decision-lab app init --template TEMPLATE.json --model MODEL.yaml
  --app-id ID --release INTEGER [--output FILE] [--force]

decision-lab app validate DEFINITION.yaml [--output FILE] [--force]

decision-lab app pack DEFINITION.yaml [--created-at ISO_TIMESTAMP] [--output FILE]

decision-lab app open PACKAGE.json [--output FILE]
```

`init` requires a packed template and canonical `{ format, module, case }` model. `--release` is a positive safe integer. The app definition retains exact supplied model source. Module validation and template restrictions apply before the app can be packed.

`open` verifies a new app package or compatible older frozen payload and emits its normalized SDK envelope. It does not install an app, alter stored data, or upgrade rules.

## Cases

```text
decision-lab case init --app APP.json [--output FILE] [--force]

decision-lab case validate --app APP.json --case CASE.yaml [--output FILE] [--force]
```

`init` copies the app's default **case-only inputs** into YAML. Edit those inputs for a new situation. `validate` verifies binding and case values against the published module and emits a validation receipt.

Case input can be case-only YAML/JSON, a full canonical model with an identical module, or a matching `decision-lab-case/1` snapshot. Changing published rules, vocabulary, presentation, or module identities requires a new app release.

## Assess without full reports

```text
decision-lab assess --app APP.json --case CASE.yaml
  [--timeout-ms INTEGER] [--run-id ID] [--created-at ISO_TIMESTAMP]
  [--output FILE] [--force]
```

Emits `decision-lab-assessment/1` with input, identity, execution outcome, and pattern assessment. It does not contain the renderer contract. All three installed patterns support `run` for complete prepared reports. Commitment runs store an explicit assessment reference into their standalone report’s lossless normalized record.

Commitment-only flags on `assess` and `run` are `--max-plans N`, `--max-scenario-checks N` and `--max-operations N`, accepting nonnegative integers within installed hard bounds. `assess --max-output-bytes N` permits a positive output ceiling up to 50,000,000 bytes. Complete assessment JSON is serialized compactly for large results, and output files remain atomic. Invalid commitment input returns failed execution and exit 2; a valid no-plan or inconsistent-basis assessment returns 0; bounded/cancelled/timed-out execution returns 3; oversized output returns 4 without a truncated file. See [Complete a Commitment](../patterns/complete-a-commitment.md).

## Run with every report

```text
decision-lab run --app APP.json --case CASE.yaml
  [--reports all] [--locale LOCALE] [--max-output-bytes INTEGER]
  [--prior-run RUN.json | --prior-input CASE.yaml] [--recompute-prior]
  [--history HISTORY.json] [--timeout-ms INTEGER] [--run-id ID]
  [--created-at ISO_TIMESTAMP] [--output FILE] [--force]
```

| Option | Meaning |
| --- | --- |
| `--reports all` | Default and only supported scope. Every retained report/selector context is included. |
| `--locale en-US` | Default locale for prepared display values. Use a locale supported by the runtime's internationalization implementation. |
| `--max-output-bytes N` | Positive safe integer, at most 50,000,000. Sets the complete output ceiling. |
| `--timeout-ms N` | Positive safe integer deadline in milliseconds; default 30,000, including worker startup and report projection. |
| `--prior-run FILE` | Use compatible archived RunBundle output for before/after comparison. |
| `--prior-input FILE` | Recompute an earlier compatible case input with the installed evaluator. Mutually exclusive with `--prior-run`. |
| `--recompute-prior` | With `--prior-run`, recompute its embedded input instead of comparing archived evaluator output. |
| `--history FILE` | Include validated retained revision metadata. It does not invent historical findings. |

Complete runs are compact JSON to retain their byte budget. A framing newline follows the JSON artifact and is outside its artifact budget. Materialization or serialization limits fail without delivering a partial output file.

```sh
decision-lab run --app marbles.app.json --case marbles.case.yaml \
  --reports all --locale en-US --timeout-ms 15000 \
  --run-id marble-review-001 --created-at 2026-11-15T00:00:00Z \
  --output marbles.run.json
```

The output has `format: decision-lab-run/1`. Build views from its `report` property; no evaluator or app package is needed for rendering. See [report output](report-output.md).

## Comparisons and history

```sh
decision-lab run --app marbles.app.json --case changed.case.yaml \
  --prior-run marbles.run.json --output changed.run.json

decision-lab run --app marbles.app.json --case changed.case.yaml \
  --prior-run marbles.run.json --recompute-prior --output recomputed.run.json

decision-lab run --app marbles.app.json --case changed.case.yaml \
  --prior-input earlier.case.yaml --output earlier-input-comparison.run.json
```

An archive must match the app, release, package, module, and supported evaluator identity/build. An incompatible evaluator archive can be compared only through explicit input recomputation. Cross-release comparisons are rejected. Archives are never rewritten by these operations.

History can be an array or `{ "revisions": [...] }`. Each release-bound entry needs `id`, `createdAt`, `modelHash`, `moduleHash`, and the exact app/release `binding` from the associated snapshot. At most 64 entries are accepted. Optional model/source snapshots must match their hashes. Explicit `{ "scope": "module", "revisions": [...] }` identifies older metadata whose release binding is unavailable. This is qualified as module-scoped metadata, not release-bound evidence of earlier conclusions.

## Workflows

The current development candidate supports these headless commands. Authoring
source, definition and run files are self-contained JSON; answer values may also
use restricted YAML. The workflow definition fixes question IDs, step IDs and
responsible roles.

```text
decision-lab workflow create --source FILE --output FILE
decision-lab workflow validate DEFINITION.json [--output FILE] [--force]
decision-lab workflow start --definition FILE [--case FILE] [--run-id ID]
  [--created-at ISO] --output FILE [--force]
decision-lab workflow answer --run FILE --question ID
  --status unanswered|unknown|awaiting-review|accepted [--value FILE]
  [--actor NAME] [--role ROLE] [--at ISO] [--note TEXT] --output FILE [--force]
decision-lab workflow prepare --run FILE --step ID [--output FILE] [--force]
decision-lab workflow evaluate --run FILE --step ID [--created-at ISO]
  [--timeout-ms N] --output FILE [--force]
decision-lab workflow review --run FILE --evaluation ID
  --status accepted|rejected --actor NAME --role ROLE [--at ISO] [--note TEXT]
  --output FILE [--force]
decision-lab workflow inspect --run FILE [--output FILE] [--force]
decision-lab workflow brief --run FILE [--output FILE] [--force]
decision-lab workflow open --run FILE [--output FILE] [--force]
```

`create`, `start`, `answer`, `evaluate` and `review` require `--output`; `-` means stdout.
`create` takes a `WorkflowDefinitionOptions` JSON object (the same input as
`lab.workflows.create`, without `contentHash`; `format` is optional), validates it through
the public SDK, and seals the resulting definition. It requires a new output
path; `--force` cannot replace an existing definition. Creating an artifact
does not certify its business meaning or publish it to a marketplace.
All workflow output is JSON. `prepare` is read only and returns exit `3` when
the step has no executable bound case. A blocked `evaluate` exits `3` with a
structured stderr diagnostic and publishes no output. Unfinished execution
retains its complete diagnostic app report with exit `3`. `inspect` returns the
entire materialized workflow output; `brief` selects its prepared brief.
`open` verifies the retained run. None of these commands automatically accepts
answers, results, or stale findings. See the
[workflow guide](../guides/run-a-workflow.md) and the business-led
[first shipment example](../guides/review-a-first-shipment.md), or the
[Walmart first-order developer journey](../guides/review-a-walmart-first-order.md).

## Workflow authoring and packages

These commands share `lab.workflows.authoring` and `lab.workflows.packages`
with the UI. They require no executor. See [Review and package a
workflow](../guides/publish-a-workflow.md) for the business review sequence.

```text
decision-lab workflow draft [--source SOURCE.json | --package PACKAGE.json]
  [--draft DRAFT.json] [--catalog CATALOG.json] [--published-at ISO]
  [--id ID] [--at ISO] --output FILE [--force]
decision-lab workflow inspect-draft --draft FILE [--published PACKAGE.json ...]
  [--output FILE] [--force]
decision-lab workflow review-binding --draft FILE --binding ID --actor NAME
  --meaning TEXT --scope TEXT --units TEXT [--at ISO] [--note TEXT]
  --output FILE [--force]
decision-lab workflow dependency-preview --draft FILE --dependency ID --app APP.json
  [--definition REVISED_SOURCE.json] [--at ISO] [--output FILE] [--force]
decision-lab workflow dependency-apply --draft FILE --preview PREVIEW.json
  --output NEW_DRAFT.json [--force]
decision-lab workflow pack --draft FILE [--published PACKAGE.json ...]
  --output FILE
decision-lab workflow package-open PACKAGE.json [--output FILE]
decision-lab workflow package-validate PACKAGE.json [--output FILE] [--force]
```

`draft` creates an editable `decision-lab-workflow-draft/1` from raw source, an
existing package, or a blank incomplete scaffold. `--draft` revises an existing
draft and retains its ID and review history; it cannot be combined with
`--package` or `--id`. Raw `--source` text may be incomplete, so a broken edit
can be saved and repaired. `--catalog` supplies `{ domain, useCase }` listing
nodes with `id`, `label` and optional `description`. `--published-at` is the
package publication time; `--at` records draft/review modification time.

`inspect-draft` returns the complete inspection. An unreviewed but structurally
valid draft exits `0` with `readyToPublish: false`; invalid configuration exits
`2` with its inspection artifact. `review-binding` records one named actor's
meaning/scope/units review against the exact current binding hash. It cannot
make an invalid source publishable. Changed bindings and dependent handoffs
require review again; prior records remain in the draft.

`pack` requires all current binding reviews, valid source and presentation,
no pending UI section edits, and a valid package envelope. Supply known releases
through repeatable `--published PACKAGE.json` on both inspection and packing.
The shared SDK then rejects a changed published ID/version, downgrades below a
known release, or corrupt release context. It does not discover release history
automatically. A blocked publication returns exit `2` and writes no package.

`draft`, `review-binding` and `pack` require `--output`; `-` means stdout.
Drafts can be replaced with `--force`. Package output and package-open output
are immutable even with `--force`. `package-validate` returns `{ valid, issues }`,
exiting `2` when invalid. `package-open` verifies and emits the unchanged wrapper,
not an authoring draft or a runtime case.

`workflow create` remains the operation for sealing a runtime definition;
`workflow pack` produces its installable marketplace envelope after reviews.
The wrapper does not include review receipts or authenticate reviewers. None
of these commands uploads or installs an item.

`dependency-preview` uses the SDK to report the affected apps, shared inputs,
mappings, dependent steps, binding reviews and brief. Optional `--definition`
supplies a complete revised workflow source for the same identity and unrelated
app pins; the replacement app must use the same installed pattern. A structurally
invalid candidate returns its preview with exit `2`. `dependency-apply` verifies
the exact base draft and untampered preview, then writes a separate draft. Both
protect all inputs, including linked aliases with `--force`. They neither accept
bindings nor publish. See [Extend a workflow's supporting review](../guides/adapt-a-supporting-app.md).

## Workflow business scenario checks

```text
decision-lab workflow check --definition DEFINITION.json --suite SUITE.yaml
  [--timeout-ms INTEGER] [--run-id ID] [--created-at ISO] [--output FILE] [--force]
decision-lab workflow check --draft DRAFT.json [--suite SUITE.yaml]
  [--draft-output NEW_DRAFT.json] [--timeout-ms INTEGER] [--run-id ID]
  [--created-at ISO] [--output FILE] [--force]
```

`--definition` and `--draft` are mutually exclusive. Definition checks require
`--suite`; draft checks can reuse the configured suite. `--draft-output` writes
the checked suite and exact result to a separate draft, using the same configured
scenario publication gate as the UI. A changed definition or suite requires
another check. All outputs protect definition, suite and draft inputs.

Suites use `decision-lab-workflow-check-suite/1` with `id`, `title` and `scenarios`.
Each scenario supplies `id`, `title`, a complete shared `case`, nonempty `expect`,
and `fixtureReviews: { answers: 'accept-supplied-fixture-values', results:
'accept-admissible-fixture-results' }`. An optional `answers` map retains explicit
`unknown`, `unanswered` or `accepted` statuses by question ID. Expectations use
`step-status` (`stepId`, `status`), `step-output` (`stepId`, safe dotted `path`,
`equals`), `brief-complete` (`value`), `brief-section` (`sectionId`, optional
`path`, `equals`) or `brief-action` (`actionId`, `present`).

The shared SDK performs the real question, app-evaluation and handoff operations
under explicitly synthetic fixture reviews. It cannot accept an inadmissible
finding or turn an unknown input into evidence. Results retain every scenario's
checks and complete workflow output, exact definition/suite hashes, summary and
qualification. These are author acceptance tests; they approve no real case.

Exit `0` means all expectations passed; `1` means a completed calculation
disagreed; `2` means invalid configuration; `3` means unavailable execution;
`4` means operational or delivery failure. A completed blocked business outcome
can pass its authored expectation. Neither native app checks nor workflow
checks replace deliberate binding review. See the [worked guide](../guides/adapt-a-supporting-app.md).

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Requested artifact delivered with completed execution, or a successful authoring operation. A diagnostic assessment for semantically invalid case values can still return `0`. |
| `1` | `app check` or `workflow check` completed a calculation that disagreed with an authored expectation. |
| `2` | Invalid arguments, syntax, validation, binding, integrity, or comparison context. Validation commands may emit an unsuccessful receipt on stdout. |
| `3` | Cancelled, timed-out, or resource-limited execution; a workflow step cannot execute, or its app evaluation is unfinished. A complete diagnostic run artifact can still be delivered. |
| `4` | Operational, worker failure, I/O, or artifact-delivery failure. |

Always inspect artifact content. Exit `0` does not mean that a claim is established or that an action is recommended. SIGINT/SIGTERM request worker cancellation. See [errors and limits](errors-and-limits.md) for response handling.

## Programmatic command runner

```js
import { runCLI, CLI_VERSION, SDK_VERSION, CLI_EXIT_CODE } from '@decision-lab/cli';

const code = await runCLI(['run', '--app', 'app.json', '--case', 'case.yaml'], {
  stdout: { write(text) { /* capture artifact text */ } },
  stderr: { write(text) { /* capture JSON diagnostics */ } },
  signal: abortController.signal,
});

if (code === CLI_EXIT_CODE.UNAVAILABLE) {
  // Inspect the retained execution diagnostics before retrying.
}
```

`runCLI` returns the documented numeric exit code and does not call `process.exit`. Its argument is an array of strings. Streams only need a `write(text)` method. For in-memory authoring or assessment without file-oriented command semantics, prefer the [SDK](sdk-api.md).

The frozen `CLI_EXIT_CODE` map names the existing values: `COMPLETED` (0),
`EXPECTATION_FAILED` (1), `INVALID_INPUT` (2), `UNAVAILABLE` (3), and
`OPERATIONAL_ERROR` (4). TypeScript consumers can import the `CLIExitCode` type.
These describe the command outcome; check the SDK assessment separately for
business feasibility, findings, and preferred options.
