# SDK API reference

Applies to `@decision-lab/sdk` **0.1.0**. The package is ESM; Node integrations require **Node 22.12.0 or later**. Start with [SDK usage](../../SDK.md) for a runnable workflow.

## Public entry points

```js
import { createDecisionLab, DecisionLabError, SDK_VERSION } from '@decision-lab/sdk';
import { createNodeExecutor } from '@decision-lab/sdk/node';
// In a browser application instead:
// import { createBrowserExecutor } from '@decision-lab/sdk/browser';
```

Import through these three entry points. Private `dist` paths are not supported API. The main entry point also exports the `evidence`, `learning`, `commitment`, `syntax`, `hashing`, and `currentApps` namespaces and public TypeScript types. The package's declarations describe the full advanced surface; this reference covers the authoring and execution services used to build applications.

## Status vocabularies

Use the public frozen maps when branching on SDK output. Their values remain
ordinary strings in JSON and YAML. Literal TypeScript types describe the same
vocabularies and retain narrowing for results with different fields.

| Owner | Constants |
| --- | --- |
| Execution | `EXECUTION_STATUS` |
| Evidence pattern | `evidence.EVIDENCE_ASSESSMENT_STATUS`, `evidence.EVIDENCE_QUERY_STATUS` |
| Learning pattern | `learning.LEARNING_ASSESSMENT_STATUS`, `learning.LEARNING_BRANCH_STATUS` |
| Commitment pattern | `commitment.COMMITMENT_ASSESSMENT_STATUS`, `commitment.COMMITMENT_FINDING`, `commitment.COMMITMENT_ERROR_CODE` |
| Workflow | `WORKFLOW_ANSWER_STATUS`, `WORKFLOW_REVIEW_STATUS`, `WORKFLOW_STEP_STATUS`, `WORKFLOW_NEXT_ACTION_KIND` |
| Workbook preview | `WORKBOOK_IMPORT_STATUS`, `WORKBOOK_STAGE_STATUS` |
| Decision presentation | `DECISION_STATUS` |

```js
import { EXECUTION_STATUS, commitment } from '@decision-lab/sdk';

if (run.execution.status === EXECUTION_STATUS.COMPLETED) {
  // Execution finished. Its business finding needs a separate check.
  if (run.assessment?.finding === commitment.COMMITMENT_FINDING.NO_FEASIBLE_PLAN) {
    // A completed assessment can establish that every listed plan fails.
  }
}
```

Assessment completion, feasibility, established preference, and recorded human
acceptance are separate conclusions. `WORKFLOW_STEP_STATUS.BLOCKED` concerns a
required handoff; a sample application's local `REVIEW_OUTCOME.BLOCKED` concerns
its business options. Keep application-specific classifications local to that
application. A workbook marked `WORKBOOK_IMPORT_STATUS.READY_FOR_REVIEW` still
needs review and application before its inputs are saved or evaluated.

## Inspect retained report completeness

```js
import { EXECUTION_STATUS, inspectReportCompleteness } from '@decision-lab/sdk';

const artifact = lab.runs.validate(run);
if (!artifact.valid) throw new Error('The imported run is invalid.');

const retention = inspectReportCompleteness(run.report);
// The same helper is available as lab.reports.inspectCompleteness(run.report).
if (run.execution.status !== EXECUTION_STATUS.COMPLETED || !retention.complete) {
  // Explain the retained diagnostics and request reassessment.
  console.error(retention.issues);
}
```

`inspectReportCompleteness(report: unknown)` returns an immutable
`ReportCompletenessReceipt`: `{complete: boolean, issues: [{code,path,message}]}`.
It checks the supported report format and explicit `materialized`,
`allRequestedViews`, `allRetainedContexts`, `truncated`, and `assessmentComplete`
flags. Missing or incorrectly typed flags cannot establish completeness.

This is a metadata check. It does not validate identity or the underlying report
schema, check a pinned app release, establish a preferred option, accept a human
review, or evaluate business rules. Keep those checks explicit. A complete report
can contain a negative finding or an unresolved answer; its completeness does
not make the business result favorable.

## Create a client

```ts
createDecisionLab(options?: { executor?: Executor }): DecisionLab
createNodeExecutor(): Executor
createBrowserExecutor(): Executor
```

The client has `sources`, `templates`, `compositions`, `collections`, `comparisons`, `apps`, `appRules`, `appChecks`, `cases`, `reports`, `runs`, `workflows`, and `workbooks` services, plus asynchronous `assess` and `run` methods. Creating a client or an idle executor does not start a worker. Authoring and validation require no executor. `assess`, `run`, `appChecks.run` and `workflows.evaluate` require an injected executor.

The SDK does not read files, persist data, install packages, or manage a marketplace. Supply objects or source text, and save returned artifacts in your application.

## Guided app requirement edits

`lab.appRules` supports bounded authoring changes to canonical
`complete-a-commitment/1` models. The browser editor and CLI use the same pure
service. No executor is required. See the runnable
[requirements walkthrough](../guides/edit-app-requirements.md).

```ts
lab.appRules.inspect(options: { model: unknown }): DeepReadonly<AppRulesInspection>
lab.appRules.preview(options: {
  model: unknown; edits: AppRuleEdits | unknown;
}): DeepReadonly<AppRulePreview>
```

`inspect` returns format `decision-lab-app-rules-inspection/1`, `modelHash`,
`supported`, requirements with their editable or advanced conditions, scalar
`refs`, table/column descriptors and current choice values. Another pattern
returns `supported: false` with a reason. Advanced expressions and shared
capacity constraints remain available through native source and are preserved
by guided changes.

Edits have format `decision-lab-app-rule-edits/1`, the complete current
`baseModelHash`, and 1–32 `changes`:

| `kind` | Payload |
| --- | --- |
| `set-requirement` | `requirement: {id,label,meaning,waivable:false}` |
| `set-condition` | `id`, `requirement`, `condition`, optional `appliesTo:{choice,values}` |
| `add-parameter` | `id`, declared input `descriptor`, explicit starter `value` |
| `add-table` | `id`, declared `descriptor:{key,columns}`, explicit starter `rows` |

Conditions are `{kind:'comparison',operator,left,right}` or
`{kind:'record',table,matches,tests?}`. Comparison operators are
`eq`, `ne`, `lt`, `lte`, `gt`, `gte`; operands are `{ref}` or scalar `{literal}`.
Record matches bind declared columns by typed equality. Optional `tests` compare
the matching row with declared references/literals. Optional choice scope
compiles to an implication: outside the listed values, that condition adds no
restriction. All operands still undergo ordinary validation and evaluation;
choice scope cannot hide undeclared references or invalid input.

`preview` rejects stale bases, malformed edits and invalid module declarations
with typed errors. It returns an immutable `decision-lab-app-rule-preview/1`
artifact with `baseModelHash`, candidate `modelHash`, complete `model`, native
YAML `source`, `changes` and `caseValidation`. Invalid existing starter values
remain visible as issues; a structurally valid candidate is a repairable draft,
not proof of a valid case or a passing business result. Nothing is saved or
published, and module versions and application identities are not changed.

## App business-scenario checks

`lab.appChecks` compares authored expectations with findings from the existing
evaluator. See the runnable [author scenario guide](../guides/check-an-adapted-app.md).
The suite is separate from ordinary case inputs and published app packages.

```ts
lab.appChecks.open(suite: unknown): DeepReadonly<AppCheckSuite>
lab.appChecks.validate(options: { suite: unknown; app?: unknown }): ValidationReceipt
lab.appChecks.run(options: {
  app: unknown; suite: unknown;
  execution?: { timeoutMs?: number; signal?: ExecutionAbortSignal };
  runId?: string; createdAt?: string;
}): Promise<DeepReadonly<AppCheckResult>>
lab.appChecks.isCurrent(options: {
  result: unknown; model: CanonicalStructure; suite: unknown;
}): boolean
lab.appChecks.matches(options: {
  result: unknown; model: CanonicalStructure; suite: unknown;
}): boolean
```

`open` validates the closed suite schema. `validate` additionally checks all
case inputs and expected references when supplied an app. `run` performs that
preflight before starting any scenario, then calculates each complete case
against the app's frozen rules. The suite allows at most 32 scenarios and 32
expectations per scenario. Only declarative expectation kinds are accepted;
there is no executable assertion language or arbitrary report-path evaluator.

Results have format `decision-lab-app-check-result/1` and status `passed`,
`failed` or `unavailable`. Each scenario retains execution metadata,
`assessmentComplete`, and checks with `expected`, `actual` and `message`.
`summary` counts scenarios. The exact model/module/source/package, suite and
SDK bindings are retained without duplicating full runs. Unfinished or invalid
assessments cannot establish a passing expectation.

`isCurrent` checks artifact integrity, status coherence and the current
model/suite/SDK basis; it accepts current failed or unavailable results too.
`matches` additionally requires every scenario to have passed. These are local
consistency checks, not authenticated approval or proof of business coverage.
Neither method runs an evaluation, publishes an app or changes saved cases.

## Workbook service

`lab.workbooks` packages an author-owned Excel interface with its exact target
and starter inputs. Case workers supply values without mapping setup. It needs
no executor. See the [mapping reference](case-workbook-mapping.md) for
the portable artifacts and [Excel guide](../guides/work-with-case-workbooks.md)
for executable standalone, workflow and comparison examples.

| Method | Inputs and result |
| --- | --- |
| `draftMapping` | `{target,case?,schema?,id?,title?,description?}` → validated author draft for supported declared inputs. |
| `releases.pack` | `{target,mapping?,starter?,starterMeaning?}` → complete immutable Excel-ready release; proves no-edit starter conversion. |
| `releases.open` | Release → verified release with exact target, workbook definition and starter inputs. |
| `releases.createCase` | `{release,caseId?,runId?,createdAt?}` → independent app CaseSnapshot, native unreviewed WorkflowRun, or comparison inputs. |
| `releases.exportData` | `{release,case?,run?,caseId?,revision?,exportedAt?}` → workbook data from explicit current inputs. |
| `validate` | Artifact and optional `{mapping,target,manifest}` context → bounded validation receipt. |
| `exportData` | `{app,mapping,case,revision?,exportedAt?}` → normalized workbook data. |
| `preview` | `{app,mapping,data,currentCase,revision?,manifest?}` → `{receipt,candidate?}`. |
| `exportWorkflowData` | `{workflow,mapping,run,exportedAt?}` → data pinned to the exact native run. |
| `previewWorkflow` | `{workflow,mapping,data,run,manifest?}` → case candidate with no transitions applied. |
| `applyWorkflow` | The same options plus `at?` → new run with changed answers submitted for review. |
| `exportComparisonData` | `{comparison,mapping,case,caseId,revision?,exportedAt?}` → one shared-case workbook. |
| `previewComparison` | `{comparison,mapping,data,currentCase,caseId,revision?,manifest?}` → shared-case candidate; no preparation. |

Node and browser entries also expose `readWorkbookFile(bytes,{mapping})` and
`writeWorkbookFile(data,{mapping})`, returning decoded data and `Uint8Array`
respectively. These adapters lazily load optional ExcelJS/JSZip dependencies;
the browser additionally requires native DEFLATE decompression support.

Preview never saves or evaluates. Workflow apply uses ordinary answer operations
and imports no acceptance or findings. The host owns explicit Apply, saving,
comparison preparation and subsequent assessment/review. A ready receipt still
retains `applied:false`. Nested child tables support declared parent-key joins,
including study report likelihoods. Generated layouts may expose a supported
subset; complex retained context continues through its normal input controls.
Unknown collections are never silently turned into empty tables.

A release contains `{format,target,mapping,starter,starterMeaning,contentHash}`.
Its `starterMeaning` is `example` or `defaults`; neither grants review acceptance.
Apps require an explicit fresh `caseId` when starting and return a bound snapshot
whose `.inputs` are raw case values. Workflows require a fresh `runId` and return
an unreviewed native run. The browser UI installs this envelope automatically;
SDK users can keep the same definition through local or remote distribution.

## Collection service

`lab.collections` is a pure organization service. It groups exact existing app
and workflow packages without changing their rules or embedded catalog metadata.
It needs no executor. See [Manage a collection](../guides/manage-a-collection.md).

```ts
lab.collections.create(options: CollectionDefinitionOptions): CollectionDefinition
lab.collections.pack(definition: unknown, options?: { createdAt?: string }): CollectionPackage
lab.collections.open(raw: unknown): CollectionPackage
lab.collections.validate(raw: unknown): ValidationReceipt
lab.collections.reference(options: CollectionReferenceOptions): CollectionMember
lab.collections.addUseCase(definition: unknown, useCase: CollectionUseCase): CollectionDefinition
lab.collections.add(definition: unknown, options: CollectionReferenceOptions): CollectionDefinition
lab.collections.remove(definition: unknown, product: CollectionProduct): CollectionDefinition
lab.collections.install(raw: unknown): InstalledCollection
lab.collections.openInstallation(raw: unknown): InstalledCollection
lab.collections.addLocalUseCase(state: unknown, useCase: CollectionUseCase,
  options?: CollectionRevisionOptions): InstalledCollection
lab.collections.addLocal(state: unknown, options: CollectionLocalMemberOptions): InstalledCollection
lab.collections.removeLocal(state: unknown, options: CollectionRemovalOptions): InstalledCollection
lab.collections.resolve(raw: unknown): ResolvedCollection
lab.collections.planUpdate(state: unknown, nextPackage: unknown): CollectionUpdatePlan
lab.collections.update(state: unknown, nextPackage: unknown,
  options?: CollectionRevisionOptions): InstalledCollection
```

Definitions contain `publisher: {id, label}`, scoped collection `id`, stable
`version`, `title`, `description`, `useCases`, `members` and optional `metadata`.
A reference option supplies `{package, useCaseId, artifact?}`; the package is
verified and its typed identity/version/hash are derived. A removal supplies
`{type: 'app' | 'workflow', id}`. Optional artifact descriptors use
`{path, bytes, sha256}` for a relative file; this is wire-file provenance, not a
network operation or proof the file exists.

`install` returns a portable `{base, revision, local}` state, with
`local: {useCases, members, hidden}`. Local operations preserve the upstream
package. Update plans expose `canApply`, changes and conflicts; admissible
updates require the same publisher/collection identity and a newer version.
They retain local members, use cases and remembered exclusions. Changing an
upstream use case's meaning under a local member also needs explicit resolution,
even without a local use-case override. Resolved rows
include `origin` and exact collection provenance.

Optional `expectedRevision` checks only the supplied installed state's revision.
It provides no shared-store compare-and-swap. The caller owns persistence and
concurrency. No operation fetches, evaluates or installs product files into UI
storage, and no operation supplies different-rules comparison.

## Rule-comparison service

`lab.comparisons` is pure: it prepares explicit mapped inputs and compares
retained findings without evaluating apps or making workflow reviews. See
[Compare authored rules](../guides/compare-authored-rules.md).

```ts
lab.comparisons.create(source: ComparisonDefinitionOptions): ComparisonDefinition
lab.comparisons.open(source: unknown): ComparisonArtifact
lab.comparisons.validate(source: unknown): ValidationReceipt
lab.comparisons.prepare(options: {
  comparison: unknown; case: JSONObject; preparationId?: string; createdAt?: string;
}): ComparisonPreparation
lab.comparisons.inputs(options: {
  preparation: unknown; variantId: string;
}): CaseSnapshot | WorkflowRun
lab.comparisons.compare(options: {
  preparation: unknown; results: Array<{ variantId: string; run: unknown }>;
}): ComparisonResult
```

The definition records common `basis: {meaning, scope}`, bounded `caseSchema`,
shared `fields`, exact product `variants` and `measures`. Fields declare
`id/path/label/meaning/scope/unit`. Each variant supplies a verified `package`,
`packageHash`, distinct product ID and an explicit input mapping:
`{value, uses, meaning, scope, units}`. `uses` accounts for every shared field;
input expressions reference only `case`. App variants share one installed
pattern; all variants are apps or all workflows. Exact template identity is
not required. Unsupported mixed products or duplicate product identities are
rejected.

Measures declare meaning/scope/unit/schema and one binding per variant:
`{variantId, value, availableWhen?}` or `{variantId, unavailableReason}`.
Output expressions may reference `case/run/assessment/report/output`. Bounded
expressions and the supported schema subset are shared with workflow/composed
authoring; there are no executable callbacks or remote references.

Decoded `run` inputs must validate as native app RunBundles or workflow runs
appropriate to their declared variant.

Preparation retains the shared case and hash, mapped inputs, per-variant
admission checks, and bound snapshots or seeded workflow runs. It starts no
native work and silently supplies no omitted shared facts. Workflow answers
still need ordinary reviews. Comparison checks native runs against the exact
prepared package and input snapshot, retains all native report information,
and materializes common cells and pairwise findings. Missing results remain
pending; unavailable native or measure findings remain explicit. Finite numeric
pairs include `delta = right - left`. No overall rank is inferred.

`complete` means every native variant is available; an intentionally unavailable
measure can remain unavailable in a complete comparison. The author declares
semantic compatibility; structural checks and hashes do not prove equivalent
business meanings or authenticate people. `uses` accounts for fields as an
author declaration; it is not a proof of dependency use. `open` rebuilds derived
preparations, cells, pairs and native summaries from the exact retained basis.
Native runs use the existing SDK validators; opening them is neither
authentication of unsigned data nor mathematical re-evaluation. Existing
`priorRun` same-release checks remain unchanged.

Public constants identify definition/preparation/result formats. Limits are
eight variants (minimum two), 64 fields, 32 measures and 50 MB per artifact,
including embedded native reports. The caller owns execution, persistence,
review interactions and presentation.

## Workflow service

The current development candidate supports headless orchestration through
`lab.workflows`. See [Run a guided decision workflow](../guides/run-a-workflow.md)
for a complete definition and SDK/CLI example. Public TypeScript declarations
define `WorkflowDefinitionOptions`, `WorkflowRun`, `WorkflowEvaluation`,
`WorkflowOutput`, and the request types below.

```ts
lab.workflows.create(options: WorkflowDefinitionOptions): WorkflowDefinition
lab.workflows.open(value: unknown): WorkflowDefinition
lab.workflows.validate(value: unknown): ValidationReceipt
lab.workflows.start(options: StartWorkflowOptions): WorkflowRun
lab.workflows.openRun(value: unknown): WorkflowRun
lab.workflows.validateRun(value: unknown): ValidationReceipt
lab.workflows.answer(options: AnswerWorkflowOptions): WorkflowRun
lab.workflows.prepare(options: { run: unknown; stepId: string }): PreparedWorkflowStep
lab.workflows.evaluate(options: EvaluateWorkflowOptions): Promise<WorkflowRun>
lab.workflows.review(options: ReviewWorkflowOptions): WorkflowRun
lab.workflows.output(options: { run: unknown }): WorkflowOutput
```

`create` accepts a definition options object. `open` and `openRun` verify existing
objects or JSON source, including exact pinned app packages and retained
history. They do not rerun evaluators. `start` seeds values as `awaiting-review`.
Answers are `unanswered`, `unknown`, `awaiting-review`, or `accepted`; only the
latter two carry `value`. Accepted answers require the question's responsible
role and a named actor. Each mutation returns a new immutable run.

`steps[].questionBindings?: Record<string, WorkflowExpression>` optionally
projects each required answer to the value tracked for reassessment. Its keys
must belong to `requires`; expressions use the input-binding context and
declared upstream dependencies. Missing keys track whole answers. The full
answer still needs acceptance, and the prepared app model and upstream review
hashes remain independent premises. See the guide's
[reassessment example](../guides/run-a-workflow.md#reassess-without-rewriting-history).

`prepare` returns a bound `case` only when inputs, binding checks and upstream
reviews permit evaluation; inspect `issues` when it is absent. A `stale` or
previously accepted step may still have a prepared case for explicit rerunning.
`evaluate` retains the full ordinary SDK run. It does not accept its result.
`review` records `accepted` or `rejected` for an exact current evaluation and
its responsible role. An incomplete, inadmissible or stale result cannot become
an accepted handoff.

`output` prepares progress, the decision brief, next actions and retained app
reports for rendering without the workflow runner. Public root exports also
include `WORKFLOW_LIMITS`, `WORKFLOW_EXPRESSION_OPERATORS`,
`createWorkflowDefinition`, `openWorkflowDefinition`,
`validateWorkflowDefinition`, `WORKFLOW_RUN_FORMAT`, and
`WORKFLOW_OUTPUT_FORMAT`. See [limits](errors-and-limits.md#workflow-bounds).

```js
const executor = createNodeExecutor();
const lab = createDecisionLab({ executor });
try {
  // Author, open, bind, and run through lab.
} finally {
  await executor.close();
}
```

## Workflow authoring and packages

These browser-portable services require no executor, filesystem or UI. They
share the Decision Lab authoring workspace's gates. See the worked
[authoring and publication guide](../guides/publish-a-workflow.md).

```ts
lab.workflows.authoring.create(options?: WorkflowDraftOptions): WorkflowDraft
lab.workflows.authoring.open(value: unknown): WorkflowDraft
lab.workflows.authoring.clone(value: unknown, options?: { id?: string; now?: string }): WorkflowDraft
lab.workflows.authoring.revise(value: unknown, changes?: WorkflowDraftRevision): WorkflowDraft
lab.workflows.authoring.inspect(value: unknown, context?: WorkflowPublicationContext): WorkflowDraftInspection
lab.workflows.authoring.review(value: unknown, review: ReviewWorkflowBindingOptions): WorkflowDraft
lab.workflows.authoring.previewDependencyUpdate(options: WorkflowDependencyUpdateOptions): WorkflowDependencyUpdatePreview
lab.workflows.authoring.applyDependencyUpdate(options: { draft: unknown; preview: unknown }): WorkflowDraft
lab.workflows.authoring.pack(value: unknown, context?: WorkflowPublicationContext): WorkflowPackage

lab.workflows.packages.open(value: unknown): WorkflowPackage
lab.workflows.packages.validate(value: unknown): ValidationReceipt
lab.workflows.packages.listing(value: unknown): WorkflowPackageListing
lab.workflows.packages.compareVersions(left: string, right: string): -1 | 0 | 1
lab.workflows.packages.create(options: CreateWorkflowPackageOptions): WorkflowPackage
```

`WorkflowDraftOptions` accepts `id`, a `definition` or existing `package`,
`catalog: { domain, useCase }`, `publishedAt` and `now`. Catalog nodes have
`id`, `label` and optional `description`; `domain` is the existing wire field
for collection placement. `create()` returns an incomplete domain-neutral
scaffold. Creating from a package preserves its declaration and publication
metadata but starts without authoring reviews.

`WorkflowDraftRevision` accepts `sourceText`, `catalog`, `publishedAt`, `title`
and `at`. Revising preserves draft identity, prior review records and pending
UI section edits. `open` validates the draft container and retains invalid or
unfinished source for repair; it does not imply the source is publishable.

An inspection contains `definition`, `package`, `valid`, `issues`, `bindings`
and `readyToPublish`. Structural `valid` excludes missing authoring reviews;
publication readiness also requires every critical binding's current hash to
match its review. Each binding exposes its exact source and destination,
meaning, scope and units. `review` requires `bindingId`, `actor`, `meaning`,
`scope`, `units`; `at` and `note` are optional. A source change stales affected
binding reviews and dependent handoffs while retaining their prior records.

`previewDependencyUpdate({ draft, dependencyId, app, definition?, at? })` previews
one exact supporting-app replacement using the same installed pattern.
`dependencyId` is the workflow alias. Optional `definition` supplies complete
revised workflow source for changing questions, mappings, forms/workbook metadata
and brief alongside the app; workflow identity and unrelated app pins remain
protected. The sealed preview contains the base draft hash, candidate draft,
validity/issues, changes and impacts: direct/downstream steps, questions,
mappings, changed native input/rule declarations, preferences, shared schema,
presentation, workbook, brief, and stale/preserved binding reviews.
`applyDependencyUpdate` recomputes the exact preview against its original draft,
rejects stale or tampered data, and returns the separate candidate. Neither
operation records review acceptance, publishes or migrates saved runs.

An optional draft `businessScenarios` contains its `suiteSource` and retained
`results`. `revise` can update this state. A configured suite requires a current
passing workflow check before packing; editing the definition or suite invalidates
that result. Drafts without a configured suite retain the existing binding gates.
See [Extend a workflow's supporting review](../guides/adapt-a-supporting-app.md).

```ts
lab.workflows.checks.validate({ definition, suite }): ValidationReceipt
lab.workflows.checks.run({ definition, suite, execution?, assessmentOptions?, runId?, createdAt? }): Promise<WorkflowCheckResults>
lab.workflows.checks.isCurrent({ definition, suite, results }): boolean
```

`run` uses the configured executor and the ordinary workflow runner. Suites use
`decision-lab-workflow-check-suite/1`, complete shared cases, independently
authored expectations, and an explicit `fixtureReviews` declaration on every
scenario. Synthetic answer/finding reviews are author test fixtures and do not
approve an operational case. Unknown answers and inadmissible handoffs remain
blocking. Expectations address step statuses/output fields, brief completion,
section values and action presence. Results retain exact definition/suite hashes,
per-scenario expected/actual checks and complete workflow outputs. `isCurrent`
validates the retained result's integrity and exact definition/suite basis.
See the [CLI suite contract](cli-commands.md#workflow-business-scenario-checks).

`WorkflowPublicationContext` supplies `publishedWorkflows`, an array of known
packages. Pass the same context to `inspect` and `pack` to reject changed
content under a published ID/version, downgrade below a known version, or a
corrupt release basis. The caller owns that context. `pack` throws
`WORKFLOW_PUBLICATION_BLOCKED` with `issues` when any gate fails.

The resulting `decision-lab-workflow-package/1` envelope contains the sealed
`workflow`, `catalog`, `publishedAt` and `contentHash`. It embeds exact app
dependencies and preserves the existing package contract. Draft reviews are
separate records. `packages.create({ workflow, catalog, publishedAt })` is a
lower-level envelope builder; it does not apply authoring reviews or release
history gates. Use `authoring.pack` for the reviewed publication path.
Hashes and declared review actors do not authenticate a publisher or reviewer.

Public root exports also include `createWorkflowDraft`, `readWorkflowDraft`,
`cloneWorkflowDraft`, `reviseWorkflowDraft`, `inspectWorkflowDraft`,
`reviewWorkflowBinding`, `exportWorkflowDraftPackage`, `createWorkflowPackage`,
`readWorkflowPackage`, `validateWorkflowPackage`, `workflowPackageListing`,
`compareWorkflowVersions` and the draft/package format and byte-limit constants.

## Source service

```ts
lab.sources.parseModel(text: string, options?: SourceOptions): CanonicalModelSource
lab.sources.parseCase(text: string, options?: SourceOptions): JSONObject | CanonicalModelSource
lab.sources.parseArtifact(text: string, options?: SourceOptions): JSONValue
lab.sources.renderJSON(value: unknown, options?: { space?: number; maxBytes?: number }): string

interface SourceOptions {
  file?: string;
  startLine?: number;
  maxBytes?: number;
}
```

`parseModel` requires the canonical `{ format, module, case }` envelope and a supported pattern identifier. `parseCase` accepts a case-only object or canonical model. Both decode the restricted YAML subset or JSON and check source format; they do **not** establish semantic validity. Invalid field values may be retained for later diagnostics.

`parseArtifact` decodes package, snapshot, and output source without verifying its declared artifact type or integrity. Follow it with the appropriate `open` or `validate` operation. `file` and `startLine` improve source locations in diagnostics.

`renderJSON` defaults to compact JSON and an 8 MiB artifact bound. `space` is an integer from 0 through 10; `maxBytes` can be raised to 50,000,000. It preserves negative zero. Use it instead of `JSON.stringify` when storing bound artifacts because normal JSON serialization converts `-0` to `0` and can change execution identity. See [bounds](errors-and-limits.md).

## Template service

```ts
lab.templates.create(options: TemplateOptions): TemplateDefinition
lab.templates.validate(definition: unknown): ValidationReceipt
lab.templates.pack(definition: unknown, metadata?: { createdAt?: string }): TemplatePackage
lab.templates.open(value: unknown): TemplatePackage

interface TemplateOptions {
  templateId: string;
  version: string; // Semantic version, for example "1.0.0".
  pattern: 'evidence-review/1' | 'assess-value-of-learning/1' | 'complete-a-commitment/1';
  title: string;
  description?: string;
  authoring?: {
    requiredModuleFields?: string[];
    guidance?: string;
  };
}
```

`create` returns an editable definition containing the installed reasoning contract. `pack` validates and freezes it into a versioned, hashed package. `open` validates an existing package and verifies its hash. These methods accept parsed data; `open`, `validate`, and `pack` also decode supplied source text.

`requiredModuleFields` adds presence requirements for known module paths, such as `assumptions` or `presentation.reports.comparison`. Required fields must be populated. Authors cannot add executable validators, replace the installed evaluator, require arbitrary unknown paths, or turn this descriptor into a custom JSON Schema. Inspect `definition.contract.schema.moduleFields` for permitted restriction paths.

```js
const template = lab.templates.pack(lab.templates.create({
  templateId: 'review-bounded-evidence',
  version: '1.0.0',
  pattern: 'evidence-review/1',
  title: 'Review bounded evidence',
  authoring: {
    requiredModuleFields: ['assumptions'],
    guidance: 'State the reviewed assumptions and the scope of the answer.',
  },
}));
```

The embedded `contract` is an **installed-validator descriptor**, not a full standalone JSON Schema. Its `structuralSlots`, `caseInputs`, capabilities, and limits explain ownership and supported authoring choices. Complete report support is provided by `run` and `reports`; the descriptor's historical report-responsibility wording is not the renderer contract.

## App service

```ts
lab.apps.create(options: {
  template: TemplatePackage;
  appId: string;
  release: number; // Positive safe integer.
  model: unknown;
  source?: string;
}): AppDefinition

lab.apps.validate(definition: unknown): ValidationReceipt
lab.apps.pack(definition: unknown, metadata?: {
  createdAt?: string;
  name?: string;
  description?: string;
  originWorkspaceId?: string | null;
}): AppPackage
lab.apps.open(value: unknown): AppPackage
```

The canonical model must match the template's pattern and pass structural module validation and template restrictions. `create` can retain invalid default case values in an editable definition. `validate` and `pack` also check publication admission and reject invalid defaults. After publication, case workers may bind invalid edited values for explicit diagnostic assessment.

If supplied, `source` must encode exactly the supplied model. Otherwise the SDK generates identified canonical source. Publication metadata describes the app without changing its rules.

```js
import { readFile } from 'node:fs/promises';

const source = await readFile('model.yaml', 'utf8');
const definition = lab.apps.create({
  template,
  appId: 'review-marble-evidence',
  release: 1,
  model: lab.sources.parseModel(source),
  source,
});
const app = lab.apps.pack(definition, { name: 'Review marble evidence' });
```

`open` verifies new app envelopes and compatible existing schema-5 app payloads/schema-1 wrappers. It returns a verified immutable envelope and preserves legacy payload identity; this does not silently migrate an old app's rules.

## Case service

```ts
lab.cases.create(options: { app: unknown; inputs?: unknown; source?: string }): CaseSnapshot
lab.cases.validate(options: { app: unknown; case: unknown }): ValidationReceipt
```

Omitting `inputs` copies the app's default case. Otherwise supply case-only inputs, a complete canonical model whose module is unchanged, or an existing `decision-lab-case/1` snapshot for the same exact app package and release.

```js
const inputs = lab.sources.parseCase(caseSource, { file: 'case.yaml' });
const snapshot = lab.cases.create({ app, inputs, source: caseSource });
const receipt = lab.cases.validate({ app, case: snapshot });
```

Snapshots retain a frozen module, case-only inputs, exact input source, app/release binding, and hashes. A snapshot that already contains source cannot also receive a separate `source` option. Case changes cannot alter module rules, presentation, vocabulary, app binding, or pattern. Change those through a new app release.

`create` can retain semantically invalid case values so a report can explain them. `validate` checks those values and returns an unsuccessful receipt. Binding or integrity failures remain errors.

## Run complete reports

```ts
lab.run(options: RunOptions): Promise<RunBundle>
```

Choose one input form:

```js
const run = await lab.run({
  app,
  case: snapshot,
  runId: 'marble-review-001',
  createdAt: '2026-11-15T00:00:00Z',
  execution: { timeoutMs: 15000 },
  reportOptions: { scope: 'all', locale: 'en-US', maxOutputBytes: 50000000 },
});
```

```js
// Unbound authoring or validated view preview:
const preview = await lab.run({ model, source, viewDefinitions });
```

The preview form has no app/package binding. Do not combine `model`, `source`, or `viewDefinitions` with `app` and `case`. Both forms support:

```ts
interface CommonRunOptions {
  runId?: string;
  createdAt?: string;
  execution?: { timeoutMs?: number; signal?: ExecutionAbortSignal };
  reportOptions?: { scope?: 'all'; locale?: string; maxOutputBytes?: number };
  context?: {
    priorRun?: unknown;
    priorInput?: unknown;
    comparisonMode?: 'recompute-prior';
    history?: unknown;
    currentDraft?: {
      sourceHash: string;
      inputHash?: string;
      diagnostics: Array<{ message: string; code?: string; path?: string }>;
    };
  };
}
```

`scope: 'all'` is the only report scope. The result contains every retained selector context, not just a currently selected screen. Consume `run.report` to build views; see the [report output contract](report-output.md).

Execution outcome and decision status are different. A resolved run can contain invalid inputs, an underdetermined answer, or cancelled reasoning. Inspect `run.execution`, `run.assessment`, `run.report.notices`, and report availability. Output-size failure rejects rather than returning a successful truncated bundle.

## Comparison context

```js
const changed = await lab.run({ app, case: changedSnapshot, context: { priorRun: run } });
const recalculated = await lab.run({
  app, case: changedSnapshot,
  context: { priorRun: run, comparisonMode: 'recompute-prior' },
});
```

- `priorRun` compares retained assessment output. It must pass run validation and match the app/release/module binding and installed evaluator identity/build.
- `priorInput` recomputes an earlier input with the installed evaluator. For a bound app run, case-only inputs and matching snapshots are accepted through the normal case-binding operation.
- `comparisonMode: 'recompute-prior'` uses a prior run's input rather than treating its archived conclusions as current evaluator output. It requires `priorRun`.
- Supply one prior source, not both. The supplied archive is never rewritten.
- `history` supplies up to 64 retained revisions. Use an array or `{ revisions: [...] }`; each release-bound entry needs `id`, `createdAt`, `modelHash`, `moduleHash`, and the same `binding` as the case snapshot. An explicit `{ scope: 'module', revisions: [...] }` can identify module-scoped historical metadata whose release binding is unavailable. Optional retained `modelSnapshot` and source identity fields must agree with their hashes. Metadata alone does not establish earlier findings.
- `currentDraft` identifies a draft that has not produced an accepted calculation. It marks the retained report as a previous calculation; it does not substitute that draft for evaluated input.

## Assessment-only operation

```ts
lab.assess(options: {
  app: unknown;
  case: unknown;
  assessmentOptions?: { maxPlans?: number; maxScenarioChecks?: number; maxOperations?: number }; // commitment only
  execution?: { timeoutMs?: number; signal?: ExecutionAbortSignal };
  runId?: string;
  createdAt?: string;
}): Promise<AssessmentArtifact>
```

This emits `decision-lab-assessment/1`: input, identity, execution, and a pattern assessment or `null`. It is not a complete report document. All three patterns support `run` and `reports.create` for complete prepared reports. Commitment runs retain their full calculation as a lossless normalized record referenced by `run.assessment`.

Commitment assessments retain the full result once in `artifact.assessment`, without duplicate `artifact.execution.result`. Invalid commitment input is failed execution with no assessment; valid infeasibility remains a completed assessment. Supplied search options add `executionInputHash`, `assessmentOptions` and `assessmentOptionsHash` to identity without changing the case's `inputHash`. Complete commitment artifact delivery permits up to 50,000,000 bytes and rejects oversize rather than truncating. Commitment `run` uses `complete-a-commitment.assessment-reference/1` instead, retaining the full lossless record in `run.report.datasets.commitment.assessment`; use `commitment.resolveCommitmentAssessment(run.assessment, run.report)` to restore it. Search options are also accepted by `run`. See [Complete a Commitment](../patterns/complete-a-commitment.md).

## Report and run validation

```ts
lab.reports.create(options: CreateReportOptions): DeepReadonly<ReportDocument>
lab.reports.validate(value: unknown): ValidationReceipt
lab.reports.decision(report: ReportDocument, options?: {
  profile?: DecisionPresentation;
}): DeepReadonly<DecisionView>
lab.runs.validate(value: unknown): ValidationReceipt
```

`reports.create` synchronously materializes reports from a compatible `model` and `assessment`. Optional fields are `identity`, `evaluatedInput`, `source`, `context`, `viewDefinitions`, and `reportOptions`. This is for callers who already hold an assessment and its exact provenance. Prefer `run` to keep evaluation and report generation in one worker job. It is not a React renderer.

Validation checks declared schemas, identities, reference closure, and supported report content. It does not prove that a source, assumption, or human-authored rule is true.

`reports.decision` selects a concise `decision-view/1` document from a complete
retained report. It requires no executor, does not rank options again, and leaves
the report intact. The public functions `projectDecisionReport(report, options)`
and `validateDecisionPresentation(profile, {model?, module?, pattern?, report?})`
are also exported from the main SDK entry point. Presentation validation returns
an ordinary `ValidationReceipt`.

The projection includes the assessment identity, status and notices, prepared
summary facts, typed comparison table, evidence questions, selected-option
detail records, prepared charts and native inspection actions. Its optional
profile defaults to `module.metadata.decisionPresentation` retained in the
report's source. The profile uses format `decision-presentation/1`; it binds
labels and existing fields without changing rules or case inputs. The React
package consumes this projection through `DecisionView`; `ReportViewer` remains
the complete report interface. See [decision-focused views](../guides/decision-focused-views.md)
for portable YAML, CLI and React examples.

## Executor interface

```ts
const task = executor.execute({ pattern: model.format, model }, {
  jobId: 'optional-job-id',
  timeoutMs: 30000,
  signal: abortController.signal,
});
const started = await task.started;
const outcome = await task.result;
task.cancel('User cancelled');
await executor.close();
```

`started` resolves `true` after a correlated worker acknowledgment before evaluation, or `false` if stopped beforehand. `result` resolves after the worker stops. `close` cancels active jobs and waits for their workers. A direct assessment job returns the original pattern assessment, not a full report. The overload for report jobs is primarily used by `lab.run`.

Options accept an optional `inputHash`, which must equal the executor's canonical job hash. Do not confuse a complete report job's hash with a case's evaluation input hash. Unsupported options or malformed nonportable input are rejected before a worker starts.

## Advanced namespaces

| Namespace | Public responsibility |
| --- | --- |
| `evidence` | Finite-relational model/case validation, source conversion, synchronous assessment, assessment comparison, presentation helpers, and connection projections. |
| `learning` | Learning model/case validation, explicit probability parsing, source conversion, synchronous assessment, basis grouping, and economic/timing projections. |
| `commitment` | Closed module/case validation and source conversion, installed semantics and limits, and synchronous complete finite-plan assessment. Complete reports, normalized assessment records and public decoding helpers. |
| `syntax` | `parseDefinitionJSON`, `parseDefinitionYAML`, and `renderDefinitionYAML`; decoding does not admit a model. |
| `hashing` | `definitionHash(source)` hashes exact UTF-8 text; `canonicalHash(value)` supplies the existing sorted-JSON identity. These do not verify a package or bind a case. |
| `currentApps` | Compatibility preparation/verification of existing frozen app payloads. It performs no persistence or installation. |

For synchronous assessment use `evidence.evaluateEvidenceModel(model)`, `learning.evaluateLearningModel(model)` or `commitment.evaluateCommitmentModel(model, options)` deliberately: they run on the calling thread. Use a worker adapter for responsive interfaces, deadlines, and hard cancellation. The [canonical model reference](canonical-yaml.md) links the three installed patterns.
