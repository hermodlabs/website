Release recovery / Jira data guide reference

Use your Jira export to review an at-risk release.

Bring remaining QA estimates into a bounded release comparison, then supply the operating facts that tickets cannot establish.

Jonathan Nacionales · 5 min read

The case in brief

At stake. Nina already has the release's remaining-work estimates in Jira. Retyping them risks a different basis for the customer call; treating the export as a complete release plan would conceal missing operating facts.

How it resolves. The supplied adapter preserves the source records and imports two workload totals. Nina adds confirmed operating inputs before calculating the four arrangements. Unknown estimates remain unknown, and a different work structure requires an adapted model.

Nina needs the release comparison for her customer call to use the team's actual remaining-work estimates. The supplied Jira adapter gives her developer a repeatable way to bring those estimates into Decision Lab while retaining their source. It does not infer a release plan from ticket status.

The path is scoped CSV → workload totals → separate operating inputs → calculated comparison. The adapter is sample code in the release-recovery repository, separate from the Marketplace's forms. There is no built-in Jira connection or Jira CSV upload in this workflow.

First check that this is your kind of release.

The current app compares four authored arrangements: full scope with existing QA, core only, full scope with additional qualified help, and a later full release. Its two work packages are core and reporting. Only a fixed four-hour independent-regression package can move to the external tester.

That structure must describe the work being assessed. A third feature package, another transferable task, different validation dependencies or another resource needs an adapted app. Renaming a CSV column cannot make an incompatible work structure fit. The extra-tester story explains why the transferable package matters.

Export the work whose meaning you can explain.

The supplied profile selects project REL, release 2026.11, build release-2026-11 and environment release-validation. Its estimate column means remaining QA hours. A development estimate or a story-point score does not have that meaning.

Inspect the complete fictional CSV alongside the mapping profile. The profile declares the column names, units, exact release scope and package meanings. Your export and reviewed mapping must agree; unrelated versions, duplicate keys and unknown packages are rejected rather than silently filtered.

Notice REL-103: its status says Done, but eight QA hours remain. The adapter retains both statements. Nina needs the team to resolve what they mean; it does not convert “Done” into zero work, completed testing or customer acceptance.

Retain a source snapshot and an incomplete case.

The adapter creates two files. A source snapshot retains issue keys, source statuses, update times, directed blocking links, units and source/profile hashes. A separate partial case carries only the two workload totals, converted to whole minutes.

A blank estimate makes that package's total unknown. Seven known hours plus an unanswered estimate do not establish a seven-hour package. Estimates in hours, minutes or seconds must convert to whole minutes; story points are rejected.

Supply what the export cannot establish.

The repository's CLI walkthrough starts a workflow with the partial case and supplies the separate operating answers. The Marketplace example exposes the same kinds of inputs through forms. Neither path should silently fill missing facts with the fictional baseline.

These facts need their own source before Nina relies on the comparison.

REL-101 blocks REL-103 in the fixture. The importer preserves that direction for review against the app's fixed validation phases; it does not construct a new schedule from arbitrary links or detect dependency cycles. An absent prerequisite such as OPS-42 remains a blocking diagnostic. A dependency structure that does not fit the authored phases needs author review and an adapted model before anyone confirms its prerequisites.

Calculate a comparison you can account for.

With the supplied estimates and separately confirmed baseline operating facts, Additional qualified help is the only supplied arrangement that passes. It costs $400 within a $500 limit and preserves the original full-scope deadline. The app establishes no ranking: Nina's stated preference to preserve scope and date explains her choice.

When an input changes, apply the new facts and recalculate before using a current finding. Keep the source snapshot with the saved analysis so the team can trace what entered the calculation. A retained timestamp does not decide whether a source is still current enough.

This is the boundary of the commitment assessment: it checks whether the declared complete arrangements meet recorded requirements. It does not verify that Jira is accurate, authenticate permission, execute tests or establish a delivery probability.

Nina can now explain which estimates came from the export and which operating facts came from elsewhere. For your next release review, bring those two sources together before making the next promise. Follow the complete adapter, mapping and workflow example in the repository.

Sources and scope

Nina, release 2026.11 and the CSV are fictional. This guide describes the supplied sample adapter and the four-arrangement release app, not a general Jira integration or arbitrary task scheduler. The Marketplace example is configured for its supplied release catalog; another organization's structure and source meanings require author review.

The complete sample source, published model and retained source manifest identify the implementation described here. The retained importer fixtures also include an unknown estimate and an external prerequisite.
